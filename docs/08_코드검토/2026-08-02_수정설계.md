1. **수정마다 "지금 실패해야 하는 테스트"를 먼저 쓴다.** 통과하면 그 수정은 아무것도 안 한 것이다.

3. **매 수정 후 269건 전량 + 재현 스크립트를 돌린다.** 실측 숫자가 바뀌면 그 자리에서 안다.

## ③ 빈 필터는 "필터 없음"이 아니라 **"0건"** 이다 (D-10)

### 설계 — 번역 계층이 결정하지 않는다

```python
class EmptyFilter(ValueError):
    """필터 값이 비어 어떤 문서도 만족할 수 없다. 0건이 정답이다 (D-10)."""

def to_chroma_where(where):
    for k, v in where.items():
        if isinstance(v, list | tuple | set):
            vals = [x for x in v if x not in (None, "")]
            if not vals:
                raise EmptyFilter(f"{k} 필터가 비었다 — 조건을 만족하는 문서가 없다")
```

- `ChromaStore.search` 가 `EmptyFilter` 를 잡아 **`[]` 반환** (로그 INFO)
- `InMemoryStore._matches` 는 이미 `False` 를 낸다 → 그대로 0건
- **두 구현이 같아진다.** 지금 갈리는 유일한 케이스가 이것이었다
- `retrieve` 노드는 "0건 = 거절"(D-46)을 이미 갖고 있으므로 **노드를 안 고쳐도 옳게 동작한다**

`continue` 로 조건을 빼는 대신 예외를 던지는 이유 — **번역기가 "이 조건은 무시해도 된다"를 판단할 자격이 없다.** 판단은 저장소가 한다.

### P4 — 함께 고칠 테스트 2건

`tests/test_retrieval_filter.py:41-44` 가 `assert to_chroma_where({"species": ["", None]}) is None` 을 **정답으로 못 박고** 주석에 *"필터가 깨지지 않는다"* 고 적어 두었다. 필터가 깨진 게 아니라 **사라진** 것이다. 단언을 `pytest.raises(EmptyFilter)` 로 바꾸고, **왜 뒤집었는지 주석에 남긴다.**

`TestInMemoryMatchesSameSemantics` 에 **빈 목록 케이스를 추가**한다 — 두 구현이 갈리는 유일한 지점인데 지금 테스트가 없다.

## ⑤ `deps.py` 의 except 절이 스스로 터지는 것 (7번)

```python
def _build_engine() -> QAEngine:
    if get_config().serve.engine != "graph":
        return StubEngine()
    try:
        from ..graph.engine import GraphEngine
        return GraphEngine()
    except Exception as e:          # ImportError · EngineNotReady · 그 밖의 기동 실패
        msg = f"serve.engine=graph 인데 GraphEngine 을 쓸 수 없다 ({type(e).__name__}). …"
        if os.getenv("PETTRIAGE_ALLOW_ENGINE_FALLBACK") != "1":
            raise EngineUnavailable(msg) from e
        log.warning("%s PETTRIAGE_ALLOW_ENGINE_FALLBACK=1 이라 스텁으로 진행한다.", msg)
    return StubEngine()
```

`except (ImportError, EngineNotReady)` 에서 `EngineNotReady` 를 **뺀다.** 그 이름은 같은 `try` 가 바인딩하는 지역 변수라 임포트가 실패하면 존재하지 않는다.

넓은 `except Exception` 이 여기서는 옳다 — **graph 를 못 만든 이유가 무엇이든 결과는 둘 중 하나**다(크게 실패 / 명시적 폴백). 지금은 좁은 except 때문에 오히려 `UnboundLocalError` 로 **둘 다 안 되고 있다.**

## ㉮ `StubEngine` 의 정량 판정 (검토 5번) → **규칙 테이블을 연결한다**

되물어 받은 체중·섭취량을 쓰지 않고 `_STUB_RULES` 의 상수를 그대로 게이트에 넣고 있었다.
4kg 개가 초콜릿 `0.1g` 을 먹든 `500g` 을 먹든 답이 `CALL_NOW` 로 같았다.

세 안을 놓고 골랐다.

| | 안 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **(a) ← 채택** | 규칙 테이블을 연결한다 (`rule_level_for` → `apply_gate`) | 정량 계산 모듈이 **처음으로 실제로 돈다.** 노드 짜기 전에 검증된다 | 04 §5 구성 A 정의에 한 문단 추가 |
| (b) | 섭취량을 **안 묻는다** | "쓰지 않을 값을 묻지 않는다" — 설계 정합. 수정 최소 | 정량 모듈이 여전히 미검증으로 남는다 |
| (c) | 그대로 두고 문서에만 명시 | 0 비용 | 시연에서 그대로 드러난다 |

**(a)를 고른 이유** — `rule_level_for`·`computable_for`·`to_mg_per_kg` 는 **실행 가능한
호출자가 저장소에 하나도 없었다.** 이 프로젝트가 가장 공들인 계산 모듈이 한 번도 실전 경로를
밟아 본 적이 없었던 것이다. 여기서 부르면 `compute` 노드를 짜는 사람이 **이미 검증된 부품**을
쓰게 된다.

### ⚠️ 배선하면서 드러난 것 — 역치의 기준이 두 종류다

`amount_g` 를 그대로 mg/kg 으로 바꾸려다 멈췄다. 규칙 테이블 12행의 기준이 갈린다.

```
양파 15-30 g/kg · 마늘 5 g/kg · 자일리톨 0.03 g/kg · 알리움 0.5%
    → 먹은 **음식의 질량**이 곧 역치의 단위다. 그대로 쓴다
초콜릿(테오브로민+카페인) 20 mg/kg
    → **테오브로민의 질량**이다. 초콜릿 질량이 아니다
```

구분하지 않고 곱하면 **초콜릿을 100% 테오브로민으로 계산**하게 된다 — 약 1만 배 과대평가다.
안전한 쪽 오류라 눈에 안 띄지만, D-51(*"잎 무게는 독소 무게가 아니다"*)이 막은 것과 같은 조작이다.

코퍼스에 다리가 있었다 — `F-034-023~025` 의 종류별 함량(베이킹 14 · 다크 5 · 밀크 2 mg/g).
그런데 **종류를 모르면 어떤 값을 골라도 우리가 만든 숫자**이므로 되묻는다.
골든셋 `G-047`(*"무슨 초콜릿인지는 모르겠어요"* → `clarify`)이 기대하던 동작이 정확히 이것이다.
