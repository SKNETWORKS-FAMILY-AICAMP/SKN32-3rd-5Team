## 2. 수집 원칙 — 3계층 관리

| 계층 | 형식 | 원칙 |
|---|---|---|
| **① 원본** | 받은 그대로 (PDF / HTML / XLSX) | **절대 수정하지 않음.** 재현성·출처 검증용 |
| **② 수집 기록** | CSV / 스프레드시트 | 출처·라이선스 기록. **본 문서 4장의 근거** |
| **③ 정규화** | CSV → JSONL | 인덱싱 입력. 최종은 JSONL로 통일 |

**공통 규칙**

- 인코딩 **UTF-8**, 파일명은 **영문·숫자·하이픈**
- **웹 자료는 반드시 스냅샷 저장** — URL은 바뀌고 내용은 개정된다. `접근일`과 함께 HTML/PDF 인쇄본 보관
- 정규화 시 **원문 인용(`quote`) 필드를 반드시 남긴다**
  → 없으면 근거 검증(sLLM ④)과 출처 표기가 작동하지 않으며, 나중에 원문 위치를 되찾을 수 없다

### 2.1 원문은 어디까지 가는가 — 적재 경로 2종 (D-37)

**모든 자료가 같은 경로로 흐르지 않는다.** 출처의 이용 조건에 따라 두 갈래로 나뉜다.

```
                    ┌─ [경로 ①] 원문 청크 적재 ──⛔ 꺼짐──✗  벡터DB
원본 · 스냅샷 ──────┤     · 자격 7건이나 **이번 범위에서는 적재 0청크** (D-45)
  (data_work/)      │
     │              └─ [경로 ②] 사실 추출 → 자체 문장화 ───→ 벡터DB external
     │                    · 복제 허락 없음(G2) — 원문은 적재하지 않는다
     │                    · **실제 적재 888청크 · 45출처** ★기본 경로
     ↓
  골든셋 채점 기준으로만 내부 사용 · 외부 배포 안 함  [D-29]
```

> **경로 ①은 자격이 없어서가 아니라 껐기 때문에 0건이다** (D-45, 2026-08-01).
> 두 경로를 함께 켜면 같은 사실이 두 번 적재되어 top-k 를 잠식하고,
> 원문의 완화 표현과 사실 표의 등급이 ④ 근거 검증에서 모순으로 잡힌다.
> **지금 벡터DB의 888청크는 전부 우리가 쓴 한국어 문장이다.**

| | 경로 ① 원문 적재 | 경로 ② 사실 추출 |
|---|---|---|
| 대상 | 오픈 라이선스 · 정부·공공 · 복제 허락 명시 | **G2에 걸린 출처** — 복제 허락이 없는 곳 |
| 벡터DB에 들어가는 것 | 원문 청크 | **우리가 쓴 문장** (D-15 문장화) |
| `quote` 필드 | 원문 인용 그대로 | **비움.** 대신 `source_id`·URL·접근일로 출처 표기 |
| 근거 | — | 저작권법 제2조1호("**표현한** 창작물") · 제7조5호 · 제28조 · 제35조의5 |

> **경로 ②에서도 원문은 버리지 않는다.** `data_work/`에 남겨
> **골든셋 채점 기준**으로 쓴다 — 04 §1.1이 요구하는 *"출처 문서에 명시된 기준을 정확히
> 인용했는가"* 는 이 원문과 대조해 검증한다. **원문은 채점표이지 적재물이 아니다.**

**단 G1a(용도 금지)에 걸린 출처는 경로 ②로도 갈 수 없다.** `repurpose`·`extract for training`
같은 문언은 재가공 자체를 금지하므로 사실 추출로도 회피되지 않는다 (D-37).

각 자료가 어느 경로인지는 **원장 `usage_scope`** 에 기록한다.

### 2.2 경로 ②의 문장화 — 템플릿을 미리 만들고 코드가 생성한다 (D-38)

**문장화를 LLM에게 시키지 않는다.** 축① *"결정론은 코드로, 판단·해석만 LLM에게"* 의 적용이다.

```
원문 ──[추출]──→ 사실 표 ──[템플릿]──→ 문장 ──→ 벡터DB
                    ↑                    ↑
              여기만 검증하면      템플릿은 한 번만
                  된다              사람이 검수
```

**템플릿은 발명하지 않고 데이터에서 도출한다.** 코퍼스의 `doc_type` 축을 그대로 쓴다 —
`toxicity_food`(27) · `nutrition`(21) · `toxicity_plant`(11) · `emergency`(9) · `symptom`(7).

```python
# toxicity_food 템플릿
"{species}에게 {substance}은(는) {risk_level}로 분류된다."
+ if threshold: "체중 1kg당 {dose}{unit} 이상 섭취 시 위험하다."
+ if signs:     "주요 증상은 {signs}이다."
+ if onset:     "증상은 {onset} 이내에 나타난다."
+ "(출처: {publisher}, {source_id})"
```

**결측 필드는 해당 절을 통째로 뺀다.** "정보 없음"이라고 쓰지 않는다 —
그 문장이 검색되면 그 자체가 오답이 된다.

> **부수 효과 하나.** 임계값 필드가 비면 정량 문장이 생성되지 않는다.
> **조류는 정량 임계치가 0건**이므로 조류 청크는 자동으로 정성 문장만 나온다.
> **D-09의 종별 분기가 데이터 단계에서 강제된다.**

**대가 하나.** 템플릿 문장은 표현이 획일적이라 임베딩 변별력이 떨어질 수 있다.
필드 값(물질명·종·증상)이 문장에 그대로 들어가고 청킹이 물질 단위(D-14)라 완화되며,
효과는 **E1(청킹 단위 비교)** 에서 *"템플릿 문장 vs 원문 청크"* 로 측정한다.

**검증은 04 §2.5(층 0)** 를 따른다 — 검증 대상은 문장이 아니라 **필드**다.

## 3. 수집 기록 시트 스키마

```
source_id, title, publisher, doc_type, species,
url, accessed_at, published_at, format, lang,
license, usage_scope, collected_by, snapshot_path, notes
```

| 필드 | 설명 |
|---|---|
| `doc_type` | `toxicity_plant` / `toxicity_food` / `nutrition` / `emergency` / `symptom` / `recall` |
| `species` | `dog` / `cat` / `bird` / `mammal` / `all` / `unknown` |
| `license` | 자료에 표기된 이용 조건. **비워두면 나중에 복원 불가** |
| `usage_scope` | 인용 가능 / 재배포 불가 / 크롤링 가능 여부 |
| `snapshot_path` | 원본 스냅샷 파일 경로 |

## 6. 라이선스 및 이용 조건

수집 자료 대부분은 **저작권이 보호되는 기관 콘텐츠**(VCA·ASPCA·Lafeber·Cornell 등)다.

**본 프로젝트의 사용 방침**

> 본 프로젝트는 **교육 목적의 비상업적 연구**이며, 수집 자료는 **인용·검증 목적으로만** 사용하고
> **재배포하지 않는다.** 각 출처의 이용약관 및 `robots.txt`를 확인하여 수집 기록에 남긴다.

**판정 절차는 `01c_데이터-작업지시.md` §6.1의 게이트를 따른다** (D-35).
차단 4단계(G1a 목적 / G1b 수단 / G2 복제 / G3 비용) + 조건 2단계(G4 DB권 / G5 개인정보).
**자료를 확보하기 전에** 통과시킨다 — S-061은 받고 분석한 뒤에 버렸다.

> ⚠️ **`artificial intelligence` 만 검색하면 놓친다.** AI를 언급하지 않고 벡터 색인을 막는 표현이
> 더 흔하다 — AVMA *"incorporate into any **information retrieval system**"*,
> FOUR PAWS *"**stored, processed** … using **electronic systems**"*, ASPCA *"must not … **store**,
> **create derivative works of**"*. 이 묶음도 함께 검색한다.

**주의 사항**

- ASPCA 식물 DB(1,024건)는 **전량 수집 금지** — 제93조 데이터베이스제작자 권리(D-34). 항목 단위 추출만
- FDA 리콜 포털은 실시간 갱신되므로 **스냅샷 시점을 반드시 기록**한다
- 재배포 사이트(Scribd 등) 경유 자료는 사용하지 않는다

## 7. 대상 종별 특성

| 종 | 특성 | 설계 함의 |
|---|---|---|
| 개 | 자료·병원 접근성 최상. 체급(toy~large) 편차 큼 | 체중 기반 용량 계산이 핵심 |
| 고양이 | 개와 독성 프로파일이 다름 (해독 경로 차이) | 개 기준의 오적용 방지가 관건 |
| **앵무새(조류)** | **진료 병원 희소, 한국어 자료 빈약** → 정보 비대칭 최대. 피식동물 특성상 **증상 은폐**. 종 자체가 체급을 결정 (모란앵무 ~50g ↔ 코카투 ~800g) | **일일 기록 기반 조기 탐지의 가치 최대**. `species_detail`·`weight_kg` 필수 |

### 7.1 조류 특이 위험 항목 — 수집 시 필수 확인

- 아보카도 (조류에 특히 위험)
- **조리기구 코팅 가열 시 발생하는 흄** (포유류에 없는 조류 고유 위험)
- **중금속(납·아연)** — 케이지·장난감·도료 노출
- 전곡·씨앗 위주 급여의 영양 불균형
- 초콜릿·카페인·알코올 등 공통 항목의 **조류 기준 수치**

### 7.2 종별 관찰 지표

| 종 | 주요 육안 관찰 지표 |
|---|---|
| 개·고양이 | 털 상태, 피부, 체취·구취, 활동량, 식욕 |
| 앵무새 | **깃털 상태, 배설물(색·형태·양), 부리·발, 호흡음, 자세** |

배설물 상태는 조류 건강의 핵심 지표이므로 기록 항목에 **별도 필드**로 둔다.

## 8. 언어 구성과 cross-lingual 대응 — **전제가 사라졌다** (D-19 후속)

**초안의 문제 설정**: *"사용자는 한국어로 묻고, 외부 문서의 90%는 영문이다."*
그래서 세 전략(사전 번역 · 다국어 임베딩 · 질의 번역)을 두고 (b)를 권고했다.

**그 전제가 D-37·D-38·D-45 로 사라졌다.**

```
경로②  원문(영문) → 사실 표(한국어 필드) → 코드 템플릿 → 한국어 문장 → 인덱스
                                                            ↑ 여기 들어가는 것은 전부 한국어다
```

원문 청크를 적재하는 경로①은 **껐다**(D-45). 따라서 **인덱스에 영문이 없고,
한국어 질의 ↔ 한국어 청크**가 된다. cross-lingual 검색이 일어날 자리가 없다.

| 초안 | 지금 |
|---|---|
| (b) 다국어 임베딩으로 cross-lingual | `bge-m3` **유지하되 근거가 바뀌었다** — cross-lingual 이 아니라 **한국어 성능** |
| (a)와 비교 실험(E2) | **폐기.** 비교할 대상이 없다 |
| 번역 태스크(⑥) 채택 조건 충족 | **미채택.** D-05 는 5종으로 확정 |

> **문서를 지우지 않고 남기는 이유** — *"왜 다국어 임베딩을 골랐나"* 는 발표에서 나올 질문이고,
> 답이 *"처음엔 cross-lingual 때문이었는데 전제가 사라져 근거를 바꿨다"* 여야 정직하다.
> 실측은 04 §2.5.3 — 한국어 질의로 0.547~0.728, 점검 14/14 통과.

## 9. 파싱 방침

| 상황 | 선택 |
|---|---|
| 포맷 10종 이상, 일단 훑어야 함 | LangChain 로더 |
| 스캔 PDF OCR, 복잡한 표 추출 | LangChain 로더 |
| **포맷이 제한적이고 구조가 명확** | **직접 코드** ← 본 프로젝트 기본 |
| 파싱 품질이 검색 성능을 좌우 | **직접 코드** |

- **내부 기록은 파싱 대상이 아니다.** 앱 입력 텍스트이며, 구조화는 sLLM ②(슬롯 추출)가 담당한다
- **외부 자료**는 HTML / PDF / XLSX가 혼재한다
  - HTML(VCA·ASPCA·Cornell 등): 표 구조가 명확 → 직접 파싱
  - PDF(AAV·WPT·FEDIAF 등): 텍스트 레이어 확인 후 직접 추출, 예외만 로더
  - XLSX(한국표준사료성분표): 파싱이 아니라 **테이블 적재** → 12장 참조
- 출력 타입은 `langchain_core.documents.Document`로 통일한다

## 10. 청킹 전략

| 대상 | 주력 청킹 단위 | 근거 |
|---|---|---|
| 독성 식물·식품 자료 | **물질(항목) 단위** | 물질 하나가 의미 완결 단위. 잘리면 **임계 용량과 증상이 분리되어 치명적** |
| 영양 기준 자료 | 종·생애단계·항목 단위 | 조건과 수치가 한 청크에 함께 있어야 함 |
| 응급·처치 가이드 | 상황·증상 단위 | |
| 질병 징후 자료 | 징후 항목 단위 | |
| **내부 일일 기록** | **1일 1청크** | 기록 단위가 곧 의미 단위. 날짜 메타데이터로 시계열 검색 |

**공통 규칙**

- **비교군**: `RecursiveCharacterTextSplitter` (500자 고정) — 베이스라인 확보용.
  주력 방식과 Recall@k를 비교하여 **청킹 근거를 실험으로 제시**한다
- 긴 항목(2000자 초과)은 하위 소제목 단위로 재분할하고, **물질명·대상 종을 접두어로 부착**
- **종 정보가 청크에서 유실되면 위험**하므로 메타데이터뿐 아니라 **본문에도 명시**한다

## 11. 메타데이터 스키마

### 11.1 외부 문서 (`external`)

```
doc_id, source_type=external,
doc_type(toxicity_plant|toxicity_food|nutrition|emergency|symptom|recall),
title, source_url, publisher, lang, accessed_at, published_at,
species(dog|cat|bird|mammal|all|unknown), species_detail,
substance, scientific_name, risk_level, threshold_unit,
section, chunk_index, quote
```

- `species`의 `mammal`은 개·고양이 공통, `all`은 전 종 공통, `unknown`은 **검수 대상**
- `species_detail` — 조류는 종 자체가 체급을 결정하므로 필수 (모란앵무 / 왕관앵무 / 회색앵무 / 코카투 등).
  개·고양이는 품종 또는 체급(toy·small·medium·large)
- `scientific_name` — 식물 자료는 **학명이 식별 키**다. ASPCA·VCA 자료가 학명 기준이므로 반드시 보존

### 11.2 내부 기록 (`internal`)

```
record_id, source_type=internal, pet_id, record_date,
record_type(diary|feeding|symptom|report),
species, species_detail, weight_kg, age_months,
extracted_slots(json), content, chunk_index
```

### 11.3 반려동물 프로필 (구조화 데이터, 벡터DB 외부)

```
pet_id, name, species(dog|cat|bird), species_detail, breed, sex,
birth_date, weight_kg, neutered, chronic_conditions[], medications[]
```

> **체중은 `weight_kg`, 섭취량은 `amount_g` 다** (D-17 후속 개정 · 2026-08-02).
>
> 원안은 *"전 구간 g 단일 단위"* 였다. 그런데 규칙 테이블(`정량임계치.csv`)의 단위가
> `mg/kg`·`g/kg` 즉 **체중당**이라, 체중을 g 로 들고 있으면 계산 노드가 매번 1000으로 나눠야 한다.
> **나눗셈을 한 번 빠뜨리는 것이 곧 1000배 오판**이고, 그것이 원안이 막으려던 사고다.
>
> 원안이 진짜로 막으려던 것은 kg/g 혼용이 아니라 **어느 쪽인지 모르는 상태**였다.
> 그래서 **필드명이 단위를 말하게** 했다 — `weight`·`amount` 같은 단위 없는 이름은 금지한다.

**필터 용도**

- `source_type` → 권한별 검색 범위 분리
- `species` → **종별 오적용 방지** (종 미확인 시 답변 금지)
- `record_date` → 시계열 조회

## 12. 정형 데이터 분리 — 계산 노드용

다음 자료는 **벡터 검색 대상이 아니라 테이블로 적재**하여 계산 노드가 조회한다.

| 자료 | 용도 |
|---|---|
| 한국표준사료성분표 (XLSX) | 원료별 영양성분 수치 조회 |
| FEDIAF 가이드라인 | 생애단계별 최소/최대 기준값 |
| 반려동물 사료 영양표준 (농진청) | 국가 공인 기준값 |
| AAFCO 기준 | 상업 사료 적합성 판별 |

> 수치를 벡터 검색으로 찾는 것은 **안티패턴**이다.
> RAG는 "이 음식이 이 종·연령에 적합한가"를, 계산 노드는 "권장 열량 대비 몇 %인가"를 담당한다 (02 참조).

## 13. 내부 데이터 설계 (가상 프로필·기록)

- **가상 반려동물 프로필 3~5건** — 종을 개·고양이·앵무새로 분산
- 각 프로필당 **누적 일일 기록 2~4주치**
- 기록에는 **의도적 시나리오**를 심는다

| 시나리오 유형 | 예시 |
|---|---|
| 정상 대조군 | 특이사항 없는 기록 |
| 급여 위험 | 사람 음식 급여 후 증상 발생 |
| 점진적 변화 | 사료 변경 후 수일에 걸친 피부·배설물 변화 |
| 조류 은폐형 | 미세 변화만 있다가 급격히 악화 |
| 판단 불가 | 정보가 부족해 되묻기가 필요한 기록 |

이 시나리오가 **골든 셋의 기록 참조형 질의**로 직결된다 (04 참조).

**개인정보**: 실제 사용자 데이터를 사용하지 않는다 (D-18). 실서비스 형태의 데모에서 입력되는
데이터는 **D-36의 처리 방침**을 따른다.

> **반려동물 정보 자체는 개인정보가 아니다.** 개인정보보호법 제2조1호가 개인정보를
> "**살아 있는 개인**에 관한 정보"로 한정하고, 제23조 민감정보의 "건강"도 **정보주체(사람)의** 건강이다.
> 동물의 진료기록은 여기에 해당하지 않는다.
>
> **위험은 동물 정보가 아니라 거기 딸려 오는 것에 있다.**

| 항목 | 근거 | 조치 |
|---|---|---|
| **동물등록번호** | 동물보호법 시행령 §11 — 등록 시 소유자 **성명·주민등록번호·주소·전화번호**가 함께 등록된다. 제2조1호 **나목**(쉽게 결합) 대상 | **수집하지 않는다.** 식별은 앱 내부 UUID |
| **사진 EXIF의 GPS** | 위치정보법 §2-2 개인위치정보 · §15①의 수범자는 "**누구든지**" | 업로드 직후 **코드가 전량 제거** |
| **사진 속 사람 얼굴** | 제2조1호 **가목** — "**영상 등**을 통하여 개인을 알아볼 수 있는 정보" | 마스킹 또는 저장 거부 |
| 보호자 본인의 건강정보 | 제23조 민감정보 | 슬롯 추출 단계에서 **폐기** |
| **LangSmith 트레이스** | 입력 원문을 그대로 저장한다 | **가명화를 켠다** — 관측 도구가 개인정보 저장소가 되지 않도록 |

**제거는 LLM이 아니라 코드가 한다** (축①). 개인정보 제거는 판단이 아니라 결정론이다.

## 14. 품질 검수 체크리스트

- ☐ 모든 레코드에 `species`가 채워져 있는가 (`unknown`은 검수 대기로 분리)
- ☐ `quote`(원문 인용)가 비어 있지 않은가
- ☐ 식물 자료에 `scientific_name`이 있는가
- ☐ 임계 용량과 증상이 같은 청크에 있는가
- ☐ 종별 기준값이 뒤섞이지 않았는가 (특히 포유류 ↔ 조류)
- ☐ 체중 단위가 `g`로 통일되었는가
- ☐ 라이선스·접근일·스냅샷 경로가 기록되었는가
- ☐ 동일 물질에 대해 출처 간 기준값이 상충하는 경우를 별도 목록으로 관리하는가

> **출처 간 기준값 상충은 문제가 아니라 좋은 실험 소재다.**
> 상충 사례를 골든 셋에 포함하면 "복수 근거 제시" 동작을 평가할 수 있다.

## 15. 미해결 사항

- ☐ 보완 수집 P0 완료 (개 응급·징후, 조류 응급·징후)

- ☐ 가상 프로필·기록 생성 완료
