## 2. 두 요건의 통합 해석

RAG와 파인튜닝은 대립하는 접근이 아니라 **역할이 다르다.**

> **지식은 RAG로, 태스크 수행 능력은 파인튜닝으로**

- 파인튜닝으로 지식을 주입하면 → 환각 발생, 갱신 불가
- RAG만 사용하면 → 모든 보조 처리에 대형 모델 필요, 비용·지연 증가

따라서 본 프로젝트의 핵심 서사를 다음과 같이 정의한다.

> ### "RAG가 근거를 가져오고, 파인튜닝한 sLLM이 그 근거가 지켜졌는지 검증한다."

이 문장으로 두 요건이 **하나의 목표(환각 방지)** 로 묶인다.
모든 산출물 문서는 이 서사에 정렬되어야 한다.

### 2.1 설계 관통 원칙 두 축

본 프로젝트의 모든 설계 결정은 다음 두 축을 따른다. 상세는 **05** 문서.

> **축① 결정론은 코드로, 판단·해석만 LLM에게**
> **축② 통제가 먼저, 배달이 나중** — 예측·검증·안전 가능한 지능을 만든 뒤에야 서비스로 내보낸다

**정지 판정 결과** — 요구사항 기준으로 붙일 조각을 판정했다.

```
채택:   0 → 1 → 2 → 3(부분) → 4 → 5(척추) → 8 → 10 → 12 → 13   (11은 선택)
미채택: 6 도구(ReAct) · 7 MCP · 9 멀티에이전트
```

미채택 근거는 05 §2에 기록한다. **"안 썼다"가 아니라 "판정해서 뺐다"로 남긴다.**

## 3. 도메인 (확정)

### 3.1 정의

> **반려동물 헬스케어 다이어리 & 응급 대응 시스템**

반려동물 보호자가 **일상 기록(브이로그·급여·관찰)을 남기면**, 그 기록과 검증된 수의학 자료를 대조하여
**영양 적정성·이상 징후·섭취 위험도**를 안내하고, 응급 상황에서는 **트리아지(응급도 분류)** 를 제공한다.

**대상 종: 개 · 고양이 · 앵무새(조류)** — 포유류 2종 + 조류 1종

| 구분 | 제안 |
|---|---|
| 원 제안 | 중독 응급 대응 QA — **이서은** |
| 확장 ① | 관찰 지표 기반 트리아지 (냄새·털·피부) — **권소라** |
| 확장 ② | 브이로그 다이어리 + 헬스케어 통합 — **오한빈** |

선정 과정·후보 비교는 `도메인검토-반려동물-헬스케어.md` 참조.

### 3.2 시스템 포지셔닝 — 반드시 지킬 원칙

> **진단하지 않는다. 검증된 문서의 근거를 제시하고 응급도만 분류한다.**

- 모든 응답에 **"참고용이며 수의학적 진단이 아님"** 고지를 노출한다
- 판정 기본값은 **안전 쪽으로 편향**시킨다 (단정보다 "관찰 필요 / 내원 권장")
- 근거가 부족하면 답하지 않고 **거절하거나 되묻는다**
- **종이 확인되지 않으면 답변하지 않는다** — 포유류 기준의 조류 오적용은 치명적

### 3.3 구현 우선순위 — 범위 관리

본 도메인의 최대 리스크는 **범위 폭증**이다. 다음 순서를 준수하며, **앞 단계 완성 전 다음 단계에 착수하지 않는다.**

| 단계 | 내용 | 위상 |
|---|---|---|
| **1. 코어** | 중독·증상 기반 응급 트리아지 QA | **반드시 완성** |
| **2. 맥락** | 개인 기록·프로필을 검색과 판정에 반영 (개인화) | 차별화 지점 |
| **3. 킬러** | 기간 요약 / 병원 방문용 리포트 | 시연 하이라이트 |
| 4. 부가 | 영양 정량 평가 | 여유 시에만 |

> **다이어리 기능 자체는 RAG가 아니라 일반 웹 앱 기능이다.**
> 기록 입력·저장·조회 이상으로 확장하지 않는다.
> **평가 기준(필수 산출물 4종) 어디에도 "앱 완성도"는 없다.**

### 3.4 선정 근거 요약

| 기준 | 평가 | 비고 |
|---|---|---|
| 내외부 문서의 자연스러운 공존 | **강함** | 개인 기록(내부) × 공적 수의학 기준(외부) |
| 데이터 확보 | 확보 진행 | 국제 권위 기관 자료 30여 건 확보 (01 참조) |
| 정답 검증 | 중 | 의학적 정확성이 아닌 **문서 충실도**로 평가 목표 재정의 (04) |
| 환각 위험성의 설득력 | **최상** | 오답의 결과가 생명 |
| 일상 페인 포인트 | **최상** | 특히 조류는 진료 병원이 희소하고 한국어 자료가 빈약 |
| 분류 체계 명확성 | **최상** | 물질 × 증상 × 위험도 × 종 다중 라벨 |

| **개인정보·보안 리스크** | **낮음** | 근로계약서·임대차 대비 명확한 우위. **개인 기록 축적 확장이 성립하는 전제** |
| 범위 관리 난이도 | **높음** ⚠️ | 3.3으로 관리 |

## 4. 시스템 개요

상세 설계는 **02** 문서에서 관리한다. 여기서는 전체 골격만 제시한다.

```
[사용자 질문 / 일일 기록]
        │
   ① 의도·위험 분류 ─────┐
   ② 슬롯 추출          │  ← 파인튜닝 sLLM
        │  (결측 → 되묻기)│
   벡터 검색 (내부 기록 + 외부 자료, species·source_type 필터)
        │                │
   ③ 컨텍스트 압축 ──────┤
        │                │
   답변 생성 + 트리아지 판정 (대형/로컬 LLM)
        │                │
   ④ 근거 검증 ──────────┘
        │
   출처 포함 응답 / 보류 / 거절
```

**파이프라인 4종**: 질의(온라인) · 인덱싱(오프라인) · 학습(오프라인) · 기록 리포트(배치)

## 7. 감점 포인트 체크리스트 (전 문서 공통 품질 기준)

- ☐ 골든 셋 없이 "잘 동작하는 것으로 보인다"로 끝나는 보고서
- ☐ 청킹 파라미터에 근거 없음
- ☐ 검색 실패와 생성 실패를 구분하지 않은 오류 분석
- ☐ 내부/외부 구분이 폴더 이름에만 있고 시스템에 미반영
- ☐ 파인튜닝 결과를 loss 곡선만으로 보고 (태스크별 지표 부재)
- ☐ 비교군(A·B·D) 없이 C 단독 성능만 제시
- ☐ 실패 사례가 전혀 없는 보고서
- ☐ 재현 불가 (버전 미고정, 시드 미설정, 실행 절차 누락)
- ☐ 아키텍처 다이어그램이 1장뿐 (파이프라인 4종 미분리)
- ☐ 고지 문구 없이 단정적으로 답하는 응답 화면
- ☐ 자료 출처·라이선스 미기재

## 9. 팀 구성 및 역할 분담

### 9.1 팀 구성

**팀명 — `save the pet`** · **프로젝트명 — `PetTriage`**

> 팀명과 프로젝트명을 분리했다.
> `save`는 구조(rescue)를 약속하는 표현이라, "본 안내는 수의학적 진단이 아닙니다"라는
> 고지 문구(02 §9)와 같은 화면에 놓이면 긴장이 생긴다.
> **팀의 지향은 팀명에, 시스템이 실제로 하는 일은 제품명에** 둔다.

| 이름 | 역할 | 담당 |
|---|---|---|
| **오한빈** | 팀장 | **전체 총괄** |
| 이서은 | 팀원 | 미정 |
| 이근준 | 팀원 | 미정 |
| 권소라 | 팀원 | 미정 |

### 9.2 워크스트림

워크스트림 5개를 4인이 분담하며, **WS5는 겸임을 전제로 한다.**
각 워크스트림 담당이 대응 문서·산출물의 1차 작성자가 된다.

| WS | 워크스트림 | 주요 작업 | 문서 | 산출물 |
|---|---|---|---|---|
| **WS1** | **데이터** | 자료 수집·라이선스 확인, 가상 프로필·기록 생성, 파싱·정제, 청킹, 임베딩, 벡터DB 적재 | 01 | ① |
| **WS2** | **RAG 파이프라인** | LangGraph 상태 그래프, 되묻기 루프, 검색·리랭킹, 프롬프트, 트리아지 판정, 거절 로직, 출처 표기 | 02 | ②③ |
| **WS3** | **sLLM 파인튜닝** | 학습 데이터 생성(distillation), 템플릿 통일, QLoRA 학습, 실험 | 03 | ③ |
| **WS4** | **평가** | 골든 셋 설계·검수, 평가 하네스, 지표 계산, 실패 분석, 비교표 | 04 | ④ |
| **WS5** | **데모 UI** | 기록 입력, 트리아지 결과 표시, 근거·출처 표시, 되묻기 UX, 거절 화면, 리포트 뷰 | 02 (UI 절) | ③ |

### 9.3 배분 원칙

- **골든 셋 100건은 전원 분담.** WS4가 설계·검수를 총괄하고 작성은 4인이 나눈다 (편향 방지 + 도메인 이해 공유)
- **부하 시점이 다르다.** 초반 WS1 → 중반 WS2 → 후반 WS3·WS4·WS5
  → 초반에는 WS3 담당이 WS1을 지원하는 형태를 권장
- **팀장은 전체 총괄**(아키텍처·일정·산출물 통합·품질 검수)을 담당한다
- **WS5는 전담을 두지 않고 겸임한다.** WS1 담당이 후반 WS5로 전환하는 배치를 권장하며, UI 스펙은 WS2와 사전 합의한다
- **1인 1산출물 원칙.** 담당자가 1차 작성, 팀장이 최종 통합·검수

### 9.4 협업 규칙

| 항목 | 규칙 |
|---|---|
| 브랜치 | `main` 보호, 작업은 `feature/<ws>-<작업명>` 브랜치에서 PR |
| 실험 기록 | LangSmith 프로젝트 공유 + 실험 로그 시트(모델·파라미터·지표·일시) 필수 |
| 환경 통일 | 의존성 버전 고정, `.env.example` 공유, 시드 고정 |
| 동기화 | 주 2회 회의 — 블로커 공유, 다음 구간 조정 |
| 문서 | 진행과 동시에 갱신, 단일 출처 원칙 준수 |
