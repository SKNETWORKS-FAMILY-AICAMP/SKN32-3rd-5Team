# eval/harness/

평가 실행 코드. 근거: `docs/04_테스트-평가계획.md` §1.2 · §4 · §7

```
run_eval.py      골든셋 → 엔진 → 채점 → 리포트
metrics.py       지표 계산 (순수 함수 · 엔진 의존 없음)
compare.py       비교군 A·C·D 표 생성          ← 아직 없다
```

## 쓰기

```bash
make eval                                        # 기본 (configs 의 serve.engine)
python eval/harness/run_eval.py --engine stub
python eval/harness/run_eval.py --only G-028 G-029
python eval/harness/run_eval.py --json eval/reports/run.json
python eval/harness/run_eval.py --fail-under 0.10   # 과소평가율 상한 (CI)
python eval/harness/run_eval.py --fail-over 15000   # answered p95 지연 상한(ms) (CI)
python eval/harness/run_eval.py --no-warmup         # 콜드 스타트를 재고 싶을 때만
```

## ⚠️ 지금 나오는 숫자는 시스템 성능이 아니다

기본 엔진 `StubEngine` 은 **물질 3종(초콜릿·포도·아보카도)만 아는 고정 지식 엔진**이다.
52건을 돌리면 대부분이 `근거없음` 으로 거절된다. 그것이 정상이고, 이 수치는
**04 §5 비교표의 구성 A(베이스라인)** 자리에 들어간다.

리포트 머리에 엔진 이름이 박히는 이유가 이것이다. 숫자만 떼어 인용하면
*"초록불이 곧 거짓 근거"* 가 된다 — 04 §2.5.6에서 실제로 한 번 겪었다.

`GraphEngine` 이 완성되면 `--engine graph` 한 마디로 갈아끼운다.
**`run_eval.py` 는 그때 손대지 않는다** — `QAEngine` 프로토콜에만 의존한다 (D-40).

## 설계 제약

- 채점 기준은 **문서 충실도**다 — *"의학적으로 옳은가"* 가 아니라
  *"출처 문서에 명시된 기준을 정확히 인용했는가"* (D-12).
- 과소평가는 **방향이 있는 오류**다. 정답보다 낮은 등급을 낸 건수를 따로 센다 (D-13).
- 추론은 `do_sample=False` 로 고정한다. 샘플링이 섞이면 재현이 성립하지 않는다.

## 이 하네스가 지키는 것 다섯

**① 분모를 섞지 않는다** (04 §1.2)

정답이 `EMERGENCY` 인데 **거절**한 건은 과소평가가 **아니다.** 등급을 낸 적이 없으므로
등급 혼동행렬에 넣을 수 없다. 그러나 사용자가 받은 결과는 *"긴급도를 못 들었다"* 이므로
**`missed_urgent` 로 따로 반드시 센다.** 섞으면 혼동행렬이 오염되고, 안 세면
과소평가율만 예쁘게 나온다.

```
🔴 과소평가율        분모 = 예측·정답 양쪽에 등급이 있는 건
▸ 등급을 못 낸 긴급 건  분모 = 정답이 CALL_NOW 이상인 건
```

**② 분모가 0이면 `0.0%` 가 아니라 `—` 다**

`_rate()` 가 `None` 을 돌려준다. `0.0` 으로 채우면 *"측정했는데 완벽했다"* 로 읽힌다.
같은 이유로 **`--fail-under` 는 등급을 낸 건이 0이면 실패한다** — 엔진이 전부 거절해도
CI 가 초록이 되는 구멍을 막는다.

**③ 슬롯을 대신 채워 주지 않는다**

`build_request()` 는 `question` 과 `species` 만 넘긴다. 체중·섭취량은 질문 문장 안에
자연어로 들어 있고, **그것을 뽑는 것이 ② 슬롯 추출 노드의 일**이다. 하네스가 파싱해
넣으면 슬롯 추출이 채점에서 빠지고 `dose` 15건이 검증하려던 경로가 통째로 사라진다.

**④ 건마다 새 세션 · 첫 응답만 채점한다**

세션을 공유하면 앞 건의 체중·종이 뒤 건에 새어 들어가 되묻기가 안 나온다 (`slot` 9건 오염).
되묻기에 답을 대신 채워 주면 `clarify` 기대 케이스가 `answered` 로 바뀌고,
**무엇을 되물었는지**도 못 본다.

## 채점 규칙

| | 통과 조건 |
|---|---|
| 상태 | `expected_status` 와 일치 |
| 등급 | `expected_triage` 가 있으면 **정확히** 일치 (인접 허용은 보조 지표) |
| 근거 | `must_cite` 중 **하나라도** 실림 (`any`). `all` 은 따로 보고 |
| 문구 | `must_contain` 전부 포함 · `must_not_contain` 하나도 없음 |

문구 채점 대상은 `scored_text()` 다 — **상승 조건은 넣고 고지 문구는 뺀다.**
`answer` 만 보면 상승 조건이 빠진 문장을 채점하게 되고
(**조건 누락은 이 도메인에서 과소평가와 같다** · D-39),
`full_text` 를 그대로 쓰면 고지 문구의 *"진단"*·*"수의사"* 가 채점을 오염시킨다.

## ⑤ 지연 — `p95` 를, 그중에서도 `answered` 를 본다

02 §12.4 로 **SSE 스트리밍을 미채택**했다. 체감 지연을 스트리밍으로 가릴 수 없고,
**실제 지연이 그대로 침묵으로 나타난다.** 그래서 숫자가 필요하다.

```
전체        p50 · p95      (n = 전 건)
answered    p50 · p95      (n = answered 만)   ← 실제 체감
노드별      p95, 느린 순    엔진이 resp.timings 를 실으면 자동
```

**평균을 안 보는 이유** — 되묻기·거절은 LLM 을 **2번**만 돌고 끝난다.
52건 중 `clarify` 9 + `none` 9 = **18건(35%)** 이 그 빠른 경로다.
섞으면 평균이 낙관적이고 **긴 답변을 받는 사람의 경험이 가려진다.**

**보간하지 않는다.** `percentile()` 은 nearest-rank 다 — 표본이 52건이라
보간하면 **실제로 관측되지 않은 지연**이 지표로 나간다. 실제 응답 하나의 값을 돌려준다.

**노드별 분해는 엔진이 줄 때만 잡는다.** 없으면 빈 값이고, **전체 지연을 노드에 배분하지 않는다** —
그건 측정이 아니라 추정이다. `GraphEngine` 이 `resp.timings` 로 실어 보내면 자동으로 붙는다.

**측정 전 워밍업 1회를 버린다** (D-53). 첫 호출에 임베딩 모델 로딩이 섞이면
`--only` 로 1건만 돌릴 때 **그 한 건이 로딩 시간으로 찍히고**, `--fail-over` 가
로딩 때문에 실패한다. **측정 도구가 자기 측정을 오염시키면 안 된다.**
콜드 스타트를 일부러 재려면 `--no-warmup`.

> **캐시를 붙이기 전에 이 숫자를 먼저 본다** (D-53).
> 측정 없이 캐시부터 붙이면 나중에 *"캐시 때문인지 원래 느린 건지"* 를 구분할 수 없다 —
> §1.2 가 검색 실패와 생성 실패를 나눈 것과 같은 이유다.
