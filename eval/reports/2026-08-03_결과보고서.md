> 2. `git status --porcelain` 이 비었는지 확인한다.
> 3. 그 커밋 해시를 아래에 적는다. **그것이 이 숫자를 재현하는 유일한 좌표다.**

> ```
>
> ✅ 측정 이후 소스를 고치지 않은 채 커밋했고 `git status --porcelain` 이 비었음을
> 확인했다. **`529510e`(측정 시점 HEAD)가 아니라 `e6600d9` 로 재현한다.**
>
> ```powershell
> git checkout e6600d949ce23bbd707d1bf0bb566407b81dce51
> pip install -e '.[api,rag,ingest,dev]' -c constraints.txt
> $env:PETTRIAGE_PROFILE="eval"
> python eval/harness/run_eval.py --arm none  --json eval/reports/재현_기준선.json
> python eval/harness/run_eval.py --arm A     --json eval/reports/재현_A.json

>
> ⚠️ `--arm A`·`A-LC` 는 `OPENAI_API_KEY` 가 필요하다. **`--arm none` 기준선은 키 없이
> 누구나 재현할 수 있다** — 코드·규칙 부분의 검증은 그것으로 충분하다.
>
> ℹ️ 이 문서에 해시를 적는 행위 자체가 다음 커밋을 만든다(`docs: 재현 커밋 기입`).
> 그 커밋은 **소스를 바꾸지 않으므로** 위 좌표는 그대로 유효하다.
>
> 숨기지 않고 적는 이유는 *"측정하지 않은 것을 0 으로 적지 않는다"* 와 같다 (04 §8).

> ⚠️ **JSON 의 `provenance.model_base_id` · `model_revision` 은 이 실행과 무관하다.**
> `provider=api` 인데 Qwen 기본값(`Qwen/Qwen3-4B`)이 그대로 기록된다. 이 실행을
> 정의하는 값은 JSON 최상위 `"model": "api:gpt-4o-mini"` 이다. 하네스의 결함이며
> 보고 대상이다 (§8) — **안 쓰는 값이 쓰는 값처럼 기록되면 나중에 이 JSON 만 보고
> Qwen 으로 잰 것으로 읽는다.**

## 2. 무엇을 어떻게 쟀나

### 2.1 분모를 섞지 않는다 (04 §1.2)

이 보고서의 비율은 **각자 다른 분모**를 쓴다. 섞으면 *"답을 안 한 것"* 이 만점으로
보고된다 — 실제로 초기 하네스가 그랬다.

| 지표 | 분모 | 왜 |
|---|---|---|
| 통과·상태 일치 | 60 (전건) | |
| 등급 일치·과소·과대 | **양쪽 다 등급이 있는 건**만 (none 25 · A 30) | 등급을 안 낸 건을 "틀렸다"로 세면 거절이 과소평가로 둔갑한다 |
| 등급 못 낸 긴급 건 | 정답이 CALL_NOW 이상인 26건 | 등급 오류가 **아니다.** 분모가 다르므로 과소평가율에 섞지 않는다 |
| must_not_contain | `answered` 만 (별도로 전체도 낸다) | 거절·되묻기는 금지 문구를 쓸 기회가 없어 **거저 통과**한다 |

> ⚠️ **A 의 등급 분모가 25 → 30 으로 늘었다.** 되묻기·거절로 빠지던 5건이 판정으로
> 들어왔다는 뜻이다. **분모가 늘어난 상태에서 일치도가 함께 올랐다**(88.0% → 90.0%)는
> 점이 중요하다 — 쉬운 건만 남겨서 오른 것이 아니다.

### 2.2 비교군 (04 §3 · D-65)

`--arm` 하나로 고르고, 그 이름이 리포트에 그대로 남는다. `arms.py` 가
`PETTRIAGE__MODEL__*` 를 **전부 비우고** 세우므로 앞 실험이 새어 들지 않는다.

| 이름 | 구성 | 상태 |
|---|---|---|
| `none` | LLM 없음 — 5태스크 전부 폴백 | ✅ 기준선 |
| `A` | gpt-4o-mini · openai SDK 직접 | ✅ 측정 |
| `A-LC` | 같은 모델을 **LangChain(`ChatOpenAI`)** 으로 | ✅ 측정 |
| `D` | Qwen3-4B 베이스 (로컬) | ❌ 미측정 (§8) |
| `C` | Qwen3-4B + LoRA 어댑터 | ❌ 미측정 (§8) |

## 3. 결과 상세

### 3.1 LLM 이 실제로 불렸는가 (05 §6)

**다른 모든 수치보다 먼저 읽어야 하는 칸이다.** 이것이 없으면 성적이 낮을 때
*모델이 못한 것*인지 *모델이 안 불린 것*인지 구분할 수 없다.

| | none | A · A-LC |
|---|---|---|
| 5태스크 전부 모델 | **0.0%** (0/60) | **100.0%** (60/60) |
| 폴백 태스크 | classify 60 · slot 55 · (raw) 41 · simplify 30 · compress 2 | **없음** |

기준선은 정의상 전부 폴백이고, A·A-LC 는 **60건 전부에서 다섯 태스크가 모두 모델을
탔다.** 아래 수치는 폴백이 섞이지 않은 값이다.

> 이 계기가 없던 동안 ①분류·②슬롯은 폴백을 **기록조차 하지 않았다.** 그래서 이서은
> 팀원이 잡은 D-73(라벨 누락으로 LLM 이 키워드 폴백보다 나빴다)이 오래 보이지 않았다.

### 3.2 트리아지

| | none | A · A-LC |
|---|---|---|
| 분모 | 25 | 30 |
| 일치 | 88.0% | **90.0%** |
| 인접(±1) | 96.0% | 96.7% |
| 🔴 과소 | 8.0% (2) | **0.0%** |
| 과대 | 4.0% (1) | 10.0% (3) |
| 🔴 중대 과소 | 0 | **0** |

기준선의 과소 2건은 **G-011**(백합·cat)·**G-017**(아보카도·bird)이고 둘 다
`rule=3 llm=None` 이었다 — 규칙이 3 에서 천장을 쳤고 올려 줄 LLM 이 없었다.
A 에서 LLM 이 4 로 올려 고쳤다. **하향 금지 게이트(D-09)가 있어야 하는 이유 그 자체다.**

### 3.3 하향 금지 게이트 — 산출물 ④의 물증

```
■ 하향 금지 게이트 (분모 26 — 규칙·LLM 둘 다 등급을 낸 건)   [A · A-LC]
  일치              11
  LLM 이 올렸다       4   (그중 과대로 끝난 것 1)
  🔒 하향 차단        5   ← LLM 이 낮추려 한 것을 게이트가 막았다
  🔒 상승 차단        6   ← 잰 자리라 막았다 (D-80. 그중 여전히 어긋난 것 0)
```

- **하향 차단 5건** — D-09 가 설계대로 작동했다는 직접 증거다. LLM 이 등급을
  낮추려 한 순간이 다섯 번 있었고 전부 막혔다. 그 결과가 **과소평가 0.0%** 다.
- **상승 차단 6건, 그중 어긋난 것 0** — D-80(잰 자리에서는 규칙이 맞다)이
  **한 건도 해를 끼치지 않았다.** 트레이드오프에 적어 둔 우려(*"역치가 한 축만
  덮는다"*)는 60건 범위에서 실현되지 않았다.
- **상승 4건 중 3건이 옳았다** — 전부 *못 잰 자리*(정성 표·양 미상 바닥)다.
  D-09 를 통째로 잠갔다면 이 3건을 잃었을 것이다. **범위를 정한 개정이 옳았다.**

### 3.4 근거·문구

| | none | A · A-LC |
|---|---|---|
| must_cite (any) | 59.0% (23/39) | 66.7% (26/39) |
| must_cite (all) | 35.9% (14/39) | 43.6% (17/39) |
| must_contain (any) | 37.5% (18/48) | **66.7%** (32/48) |
| must_contain (all) | 4.2% (2/48) | 8.3% (4/48) |
| must_not_contain *(answered)* | 92.3% (24/26) | 93.5% (29/31) |
| must_not_contain *(전체)* | 95.6% (43/45) | 95.6% (43/45) |

`must_contain (any)` 가 37.5% → 66.7% 로 가장 크게 올랐다 — 폴백 경로에서는
`draft = context` 라 검색 원문이 그대로 나갔고, LLM 이 붙자 질문에 답하는 문장이
만들어졌다는 뜻이다.

> ⚠️ **`must_contain (all)` 8.3% 는 시스템 성능으로 읽지 않는다.** 한 케이스가 요구하는
> 문구를 *전부* 포함하라는 조건이고, 골든셋의 문구 목록이 지나치게 촘촘한지
> 함께 봐야 한다 (§8 남은 과제).

### 3.5 지연 (02 §12.4)

| | none | A | A-LC |
|---|---|---|---|
| 전체 p50 / p95 | 150 ms / 232 ms | 7.23 s / 10.23 s | 8.34 s / 10.83 s |
| answered p50 / p95 | 155 ms / 215 ms | **8.38 s** / 12.79 s | **9.24 s** / 12.89 s |

**되묻기·거절을 섞지 않고 `answered` 를 따로 냈다.** 거절은 LLM 을 두 번만 돌아 빠르고,
섞으면 평균이 낙관적으로 나와 **긴 답변을 기다리는 사람의 경험이 가려진다.**

02 §12.4 로 스트리밍을 쓰지 않으므로 이 값이 그대로 **침묵**이다. 8.4 초 동안 화면에
아무것도 나오지 않는다. 응급 상황에서 이 침묵은 그 자체로 설계 결함이다 (§8).

### 3.6 종별 (04 §4.2 — 전체 평균은 조류 저하를 가린다)

| 종 | n | 통과 (none → A) | 등급 일치 (none → A) | 과대 (A) |
|---|---|---|---|---|
| dog | 30 | 10.0% → **46.7%** | 100.0% → 94.1% | 5.9% |
| cat | 17 | 35.3% → 41.2% | 83.3% → 87.5% | 12.5% |

**조류가 가장 약하다.** 코퍼스의 조류 정량 역치가 0행이라 정성 표에만 의존하고
(D-09 개정), 그래서 D-78·D-80 의 정량 개선이 조류에는 닿지 않는다. 전체 평균만
보면 이 사실이 가려지므로 종별을 반드시 따로 낸다.

## 4. A vs A-LC — 추상이 실제로 갈아끼워지는가

**두 실행의 채점 결과가 완전히 같다.** 통과 27/60, 실패 33건의 **case_id 까지 동일**,
게이트 감사 수치도 동일하다. 차이는 지연 하나뿐이다 (p50 7.23 s → 8.34 s).

| | A (openai SDK) | A-LC (LangChain `ChatOpenAI`) |
|---|---|---|
| 통과 | 27/60 | 27/60 |
| 등급 일치 | 90.0% | 90.0% |
| 실패 목록 | 33건 | **같은 33건** |
| 게이트 | 11 / 4 / 5 / 6 | **같음** |
| answered p50 | 8.38 s | 9.24 s |

이것이 뜻하는 것 —

1. **필수 산출물 *"LangChain 을 활용하여 벡터DB와 LLM 연동"* 이 동작으로 증명된다.**
   D-71 로 정한 대로 LangChain 은 **LLM 연동에만** 쓰고 벡터DB는 직접 다룬다.
2. **`LLMClient` 프로토콜 뒤에서 구현을 바꿔도 결과가 같다** (D-21). 결과가 달랐다면
   둘 중 하나가 프롬프트를 바꾸고 있다는 뜻이었을 것이다.
3. 지연 차이 약 0.9 초는 LangChain 계층의 오버헤드로 보이며, 정확도에는 영향이 없다.

## 5. 실패 분석 (04 §7)

A·A-LC 의 실패 33건을 원인별로 넷으로 묶는다. **묶음마다 손댈 곳이 다르다.**

### ① `refused → clarify` 6건 — 🔴 설계 미결 (D-46)

`G-020 · G-026 · G-049 · G-050 · G-051 · G-052` (전부 `none` 유형)

*"우리가 다룰 질문이 아니다"* 로 거절해야 하는데 되묻기로 빠진다.
**기준선 7건 → A 6건.** LLM 분류를 붙였는데 **1건밖에 줄지 않았다.**

> 원인은 모델이 아니다. **`intent=general` 이 곧 거절인가에 대한 판정 기준이 없다**
> (D-46 이 ①분류에 넘겼으나 기준을 정하지 않았다 — 06 §8 결정 대기 목록).
> 기준 없이 모델을 바꿔도 이 6건은 움직이지 않는다.

### ② `answered → refused` 8건 — 검색·물질 동정 실패

`G-004 · G-007 · G-012 · G-021 · G-042 · G-046 · G-104 · G-108`

답해야 하는데 근거를 못 물어 거절했다. `prevent` 3건이 **전부 여기 있다**

검색·판정 경로와 성격이 다르다.

### ③ `clarify → answered` 5건 — 골든셋 정정 후보

`G-003 · G-016 · G-023 · G-047 · G-101`

**기준선과 A 에서 동일하게 나타난다** — 모델과 무관하다는 뜻이다. 이전 검토에서
*G-003 · G-023 · G-047 은 시스템이 맞고 G-016 은 골든셋이 맞다* 로 정리해 둔 건들이다.
마감 전 골든셋 정정 대상 (04a 지침에 따라 근거를 적어 수정한다).

### ④ `근거/문구` 9건 — 채점 기준 재검토 필요

`G-005 · G-008 · G-014 · G-017 · G-019 · G-041 · G-043 · G-044 · G-048`

8.3% 인 것과 같은 신호이며, **시스템과 골든셋 양쪽을 봐야 한다.**

### ⑤ 등급 오류 3건 — **전부 정량이 아닌 자리**

## 6. 한계 — 이 숫자를 어떻게 읽지 말아야 하는가

1. **표본 60건.** 유형별 분모가 3~15건이라 `prevent`(3) · `symptom`(3) 의 비율은
   1건 차이로 33%p 씩 움직인다. 유형별 수치는 **방향만** 읽는다.
2. **골든셋과 코퍼스가 같은 자료에서 나왔다.** 초콜릿 4건이 `F-034-020~026` 에
   정확히 떨어지는 것은 검산으로는 의미가 있으나, **일반화 성능의 근거는 아니다.**
3. **`none` 기준선의 ④ 근거 검증은 무의미하다.** 폴백에서는 `draft = context` 라
   판정이 항상 `근거있음` 이고, 근거없음 탐지 재현율은 **0인 채 초록으로 보인다.**
4. **지연 8.4 초는 측정 조건이 최선일 때의 값이다.** 워밍업 1회를 버렸고 API 한도에
   걸리지 않은 실행이다.
5. **비교군 C·D 는 재지 못했다** (§8). 따라서 *"sLLM 파인튜닝이 대형 LLM 을 대체할 수
   있는가"* 에는 아직 답하지 못한다.

## 9. 결론

1. **RAG + 규칙 + LLM 의 분업이 수치로 성립한다.** 기준선 대비 통과 23.3% → 45.0%,
   과소평가 8.0% → **0.0%**, 등급을 못 낸 긴급 건 26.9% → 11.5%.
2. **안전 목표를 달성했다.** 🔴 중대 과소 **0건**, 과소평가 **0.0%**. 하향 금지 게이트가
   실제로 5회 작동한 기록이 남아 있다.
3. **수치 판정은 코드가, 문장은 LLM 이** — 이 분업이 `dose` 유형 등급 일치 100% ·
   과대 0% 로 확인된다. 반대로 계산이 없는 자리(`fact`·`bird`)가 가장 약하다.
4. **LangChain 연동이 동일 결과로 증명된다** (A ≡ A-LC).
5. 남은 실패의 다수는 **모델이 아니라 미결 설계와 골든셋**에 있다 (§5 ①③④ = 20건).
